## Reproducing any number

* Full suite, canonical order: `needle-board run N -- bash .auto/measure.sh` (inside the wrapper, so
  `$FLASH_PORT`/`$SERIAL_PORT` and the board lock are set). Restricted screen: `AUTO_GROUPS=primary`.
  A repeat of an already-measured image needs `AUTO_ALLOW_REPEAT=1` plus a reason.
* Host quality gates: `bash .auto/checks.sh` (host 19/19, fidelity probe, prefix isolation).
* CQ2 kernel differential (per tree): hoist the shape sweep in **that tree's own** `kbench.c`
  (the two lines in `.auto/exp96/kbench.c.sweep-hoisted`), build a throwaway dir with
  `-DNEEDLE_KBENCH=ON -DNEEDLE_KBENCH_ASM=1`, and look for
  `KB NUM ... kernel=tie1n exact=768/768 bitexact=1`.
* Behavioural capture: `serial_api.py` on the board's **own** console node inside its lock, then
  `demo/capture.py` unchanged (it speaks HTTP on 127.0.0.1:8081). Kill the `serial_api.py` children by
  PID afterwards - `pkill -f needle-api` misses them and the console stays claimed.
* Board attach (any status/request work): `tools/serial_api.py`'s `Device` with the constructor kept
  **closed** and DTR/RTS false before and after the open. Any other open discipline resets the chip and
  can leave it in ROM download mode, which looks exactly like a dead board.

# CORRECTION to the capture recipe (learned the hard way, 2026-09-28 evening)

**Do NOT run an `AUTO_SAVE=1` capture from the main checkout.** Main's `engine/` is a **stale
lineage** - it contains none of this campaign's engine work (no EG2, no `qk_dot8`, no amortised loop;
those live only in the workers) - so goldens captured there would encode a *different engine's*
behaviour while looking perfectly valid. The attempt was stopped by the harness's own
`PROVENANCE_MISMATCH` gate, which is the second time this session that gate has earned its keep.

**The correct procedure for recording the four missing device goldens** (the #467 additions
`heldout_free_describe`, `heldout_translate_de`, `heldout_probe_reading`, `heldout_status_open`):

1. Work **in a worker** (board 1 is the natural one: its tree carries the lossless RX ring, which is
   what lets a 24-case session complete in one boot).
2. Copy **main's** `.auto/prompts.json` (24 cases) into that worker, and copy main's
   `.auto/golden/host.json` too if it differs - the four cases have host goldens but no device goldens.
3. Delete the worker's stale `.auto/expect_engine_md5` (a stale expectation aborts the run - that is
   what happened here - and it must not be papered over: pin the worker's own PROV_ENGINE instead).
4. Run the **full group set** in canonical order with `AUTO_SAVE=1` (the partial-save guard refuses
   anything less) so the four device goldens are recorded together with the existing ones.
5. Then re-run the pre-existing cases and prove none drifted, and commit prompts + goldens **together**
   - never the prompts alone, which is the rule this half-captured state violated originally.
6. Finally, sync the completed set back to main and to the other two workers so all four copies agree.

**Verified facts behind this recipe:** the workers' suites are already complete (20 cases each, zero
missing device goldens; the only absent host golden is `think_timer60`, which is device-only by design);
main carries 24 cases with 4 missing device goldens; and board 1's firmware is a candidate tree with the
ring, so the session can complete.

# SNAPSHOT STALENESS -- found and fixed (2026-09-28 late)

**The gap:** `.auto/trees/verify.sh` compared each snapshot only against the hash embedded in its
filename, so it reported `SNAPSHOT_OK` while board 3's live tree had already moved on (its
`qk_hd == 48` specialization landed after the snapshot). A recovery artifact that no longer matches
the tree it is supposed to recover is the failure mode the snapshots exist to prevent - and this is the
sixth instance this session of something silently meaning less than it claims.

**Fixes, both verified:** board 3 re-snapshotted as `board3-ad9804745c88.tar.gz` (its live hash), and
`verify.sh` gained a `--live` mode that hashes each worker's current sources and reports `LIVE_DRIFT`
on a mismatch instead of stopping at internal consistency. Both modes now pass:

```
$ bash .auto/trees/verify.sh            # snapshot internal consistency
$ bash .auto/trees/verify.sh --live     # snapshots vs the live workers
LIVE_MATCH board1 hash=efa82fec3f6a
LIVE_MATCH board2 hash=a01263caeaf7
LIVE_MATCH board3 hash=ad9804745c88
```

**Board 3's pin is unchanged at 6.1450:** the specialization it carries was measured as a **null** on
that tree (6.1450 -> 6.1450, #844). It stays in the tree because it is harmless, but only its hash
moved, not its number. **Run `verify.sh --live` before any handover** - it is now the check that the
recovery path still points at the trees that exist.

# THE QUANTIFIED TOKEN MODEL (2026-09-28) -- every phase reconciled against measured per-call costs

Built with the #852 rule in force: no rate derived from a multi-purpose timer, and every number below
is either a measured per-call cost from the campaign's kbench/counters or a count from the archive.
The token is ~163 ms at the best tree; the table shows why, and why none of it is addressable.

| phase | measured ms | model | reconciliation |
|---|---|---|---|
| **proj2bit** | 79.7 | 14.36 M weights x 2 instructions = 28.7 M instr; at the walker's measured 1.35-1.5 IPC | 79.7 ms = 19.1 Mcycles -> 1.50 IPC. 24 forced ALU ops per 16 weights = 12 issue cycles + ~4 slack = the measured 16 |
| **attention** | 23.5 | QK: 14 400 dots x measured 139 cyc = 2.0 Mcyc = 8.3 ms; exp pairing 8 500 pairs x 198 cyc; P.V + staging the rest | QK alone is 8.3 of the 23.5 ms; the dot runs at 2.90 cycles/MAC (35 % of FPU peak) and is latency-bound |
| **hadamard** | 20.2 | `kron_apply` at a measured ~1 madd per product (8 madd.s per 8 products) | ~0.75-1.5 overhead instructions per product; wider forms lost to register pressure |
| **engram** | 14.6 | 2.36 M weights x 2 instructions | 14.6 ms = 3.5 Mcycles -> 1.35 IPC, the same kernel as proj2bit |
| **phi** | 8.1 | `nd_cq_prepare` + LUT build + 73.7 K weights at ~4.1 instr/weight | cannot be priced per weight from this timer (its bracket is not single-purpose) |
| **sinkhorn** | 3.0-3.7 | 3 786 exp x ~99 cyc + 1 280 logf x ~350 cyc = **3.43 ms** | **matches the measurement** - the phase is fully explained by its transcendental calls |
| **prep+lut** | 1.7-4.2 | 10-24 calls x measured 37.4 kcyc = 1.56-3.75 ms | the call count sits inside the measured range |
| mix / step-tail / rope | 2.8 | swept; rope is 24 libm calls per token shared by every layer | measured and closed |

**Three properties make this a useful artifact.** (1) Every entry is a *reconciliation*, not an
estimate: the model reproduces the measured phase time or explains why that timer cannot be used for
the purpose. (2) The two phases that are pure walker work agree on the same effective IPC (1.50 and
1.35), so the walker's cost model generalises across the model wherever it applies. (3) Nothing in the
table is addressable without changing what is stored: proj2bit's budget is forced by the ISA's
addressing model, attention's by load latency that the compiler already schedules best, hadamard's by
register pressure, engram's is the same kernel as proj2bit, sinkhorn's is transcendental calls that are
bit-exactness-locked, and phi's residual is delivery that needs ~18 KB/core it does not have.

**Use it this way:** before proposing anything, find the phase it targets in this table and read the
model column. If the proposal does not change a count in that column, the phase has already been shown
to be insensitive to it.

## The one decision

The two frozen cases (`heldout_interval_one`, `heldout_long_tools_note_only`) diverge whenever the
lossless RX ring is present, and **six probes have ruled out**: backlog and per-request timing (5 s gaps
change nothing), input differences, nondeterminism, order dependence, and heap layout (the ring is
installed after the model's allocations). The mechanism is unidentified and **the decision does not
depend on it**. Options: (a) keep the ring and re-baseline/replace those two cases - the ring is what
fixed the >128-byte request wedge and made a 20-case suite completable; (b) drop the ring, losing that
fix and the suite; (c) keep them as blockers.
